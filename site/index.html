appd(1)

Systemd application manager

Version 0.2.7 · Linux · MIT

One JSON file in. One hardened systemd unit out.

Name

appd — describe a service in JSON; get a hardened systemd unit, a system account, and a state directory.

Synopsis

shell 
cargo install --locked appd
sudo "$(command -v appd)" install

No Rust on the host? Take the static binary. It is a single file; copy it, run appd install, and continue. install also creates /etc/appd.

config
/etc/appd/my-app-service.json
unit
appd-my-app-service.service
account
appd-my-app-service
state
/var/lib/appd-my-app-service

Quickstart

  1. Write one config.

    Save this as /etc/appd/my-app-service.json, mode 0600. The filename is the app name. The name is a stand-in; use your own project name.

    json 
    {
  "description": "My app service",
  "exec": "/srv/my-app-service/bin/my-app-service",
  "args": ["--bind", "127.0.0.1:8787"],
  "restart": "on-failure",
  "permissions": {
    "network": true
  }
}

  2. Check it.

    Doctor reads the config without writing anything. It catches missing paths, env files, accounts, and unusable binaries.

    shell 
    sudo appd doctor

  3. Write the unit.

    Apply renders /etc/systemd/system/appd-my-app-service.service and reloads systemd. It starts nothing.

    shell 
    sudo appd apply my-app-service

  4. Start it.

    Enabling and starting are separate decisions, and separate commands.

    shell 
    sudo appd enable my-app-service
sudo appd start my-app-service

`apply` synchronizes unit files. It never restarts a running service. `appd diff` shows what would change; `appd restart` is the follow-up.

Illustrative, and limited to fields appd actually renders. With network off, the unit still allows AF_UNIX; there is no wider directive to revoke.

Description

A systemd unit is a small security policy with a command attached. appd makes the policy the part you write first.

You describe the service once: binary, arguments, working directory, environment, the paths it may write, whether it may open a socket. appd renders that into a namespaced unit under /etc/systemd/system/, provisions an unprivileged account if you did not name one, and lets systemd run it.

There is no database and no agent. The config is the source, the unit is the artifact, and the journal is the log. appd diff compares the first two.

What it removes

unit-file archaeology
One JSON config per app, one generated unit, one predictable name.
group operations
appd restart all, appd status all, appd apply all — no unit-name roulette.
the supervisor trade-off
Group control without giving up systemd's sandbox.
hardening drift
The sandbox is closed by default. Every path, device, or socket is an explicit line in the config, visible in appd diff.
name collisions
Every unit is prefixed appd- and marked. appd refuses to overwrite a unit it did not write.
shared accounts
Each app gets an appd-<app> system account with no shell and no home.
stale units
Rename a config and the old unit is reported as an orphan; appd apply --prune removes it.
journalctl flags
appd logs and appd error-logs instead of remembering -u, -xe, and -p.

The live transform above is the whole unit, not an excerpt: every hardening directive, every permission, and the install target.

Philosophy

Simplify the service. Keep the sandbox.

systemctl is exact, but it makes you hold the whole estate in your head: unit names, per-service restart commands, and hardening lines copied from somewhere until the service starts. supervisorctl gives you group control, then asks you to trade away the sandbox systemd already provides.

appd is the wrapper that closes both gaps. One config per app, generation and management from one place, the familiar command shape (status, restart, enable), a TUI when you want to watch the estate, and group operations that actually work: appd restart all. Call it the Swiss army knife for services on a single box.

Security is provisioned first, not bolted on. A dedicated appd-<app> account, a private writable state directory, ProtectSystem=strict, ProtectHome, PrivateDevices, NoNewPrivileges. Every exception is a line in the JSON and a line in appd diff.

If you're using cloud services and containers, great. If you're running long-lived services on a Linux box, this is for you.

appd is a CLI today; a daemon is planned as a mode of the same binary. Until then, systemd is the daemon, and the unit files are the state.

What it is not

  • Not a service manager. systemd runs the service; appd writes the unit.
  • No --user units. System scope only.
  • No ordering between apps (after / requires) yet.
  • journald only; no file-backed logging or rotation to manage.
  • No AppArmor generation. It attaches an existing profile by name.
  • No telemetry, no account, no background process.
